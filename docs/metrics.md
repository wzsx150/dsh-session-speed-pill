# 每个数字是怎么算出来的

本文把弹层与胶囊里的每一项，从**原始会话事件**逐层推到显示值，并给出一轮真实对话的完整算例。
所有结论都可以用会话日志复算；文末给出复算方法。

---

## 0. 数据来源

| 事件 | 取出什么 |
|---|---|
| `turn/start` / `turn/end` | `time` → 一轮的墙钟 |
| `step/start` | `time` → 一次模型请求的起点 |
| `assistant/message` | `time`、`usage`、`stream` |
| `tool/call` / `tool/result` | `callId`、`message.toolCallId`、`time` → 工具执行时间 |
| `usage` | `inputTokens`、`outputTokens`、`cacheReadTokens`、`cacheWriteTokens` |
| `stream` | `time0` / `dt[]`（增量时间线）与 `chunk`（绝对时间的原始块） |

`usage` 恒等式（日志实证）：`totalTokens = input + cacheRead + cacheWrite + output`。
官方语言包把 `message.turnUsage.input` 叫「未缓存输入」——`inputTokens` **不含**缓存命中。

## 1. 时间轴的语义（有硬证据）

- `{ type: "chunk", time, chunk }` —— 原始块，`time` 是绝对时间戳
- `{ type: "text-chunks" | … , time0, dt[], texts[] }` —— 增量时间线

在 26 轮 294 条记录上验证：

| 检验 | 实测 | 结论 |
|---|---|---|
| `time0` vs 同 index 的 `block-start.time` | 51 次相同，243 次差 **1 ms** | `time0` ≈ 块起始时刻 |
| `dt[0] === 0` | 92 / 294 | `dt[0]` 是「块起始 → 首个增量」的间隔 |
| `message.time` − 末块时间 | 中位 **22 ms**，p95 85 ms | 用末块而非提交时刻更准 |

```
第 i 个增量时间 = time0 + Σ dt[0..i]
首块 = min(time0 + dt[0])      末块 = max(time0 + Σ dt)
```

## 2. 预填充是**估算**，不是测量

日志里没有任何字段直接给出预填充耗时，所以这一项只能估。

**采用的口径**：`未缓存输入 ÷ 首字延迟`。

因为 `TTFT = 固定延迟（网络+排队） + 预填充 + 首 token 生成`，分母必然大于等于真正的预填充时间，
所以这个比值是真实预填充速度的**下界**——真实的只会更快。面板与脚注都标了「估算」。

**为什么不用回归**：用 606 步做 `TTFT = a + b × promptToken` 的最小二乘拟合，

```
a = 1269 ms    b = 1.177 ms / 千 token    r = 0.210    R² = 0.044
```

R² 只有 0.044——prompt 规模只能解释 4% 的 TTFT 波动，斜率估出来的 849 tok/s 噪声过大，不采用。

**为什么不用 `block-start`**：曾假设「提供方开始响应」等于「预填充结束」，用 151 步验证该假设：

| 相关性 | 值 |
|---|---:|
| `corr(未缓存输入, 请求→block-start)` | **0.008** |
| `corr(未缓存输入, block-start→首内容)` | 0.076 |

按输入分桶，`请求→block-start` 的中位几乎不随 prompt 变化（0–500 步 408 ms，2 万以上 817 ms）。
若它代表预填充，必须随 prompt 线性增长；相关系数 0.008 说明它只是网络与排队抖动。
把它当分母会算出超过 1,000,000 tok/s 的荒谬值——所以**不用**。

## 3. 每个参数的定义

| 显示项 | 公式 | 依赖 |
|---|---|---|
| **总耗时** | `turnEnd.time − turnStart.time` | 轮边界 |
| **模型耗时** | `Σ_s (s.last − s.start)` | 首个内容块到末块，含首字延迟与网络 |
| **工具耗时** | `总耗时 − 模型耗时`（≥0） | 残差，含工具执行与其间的调度、审批、重试 |
| **首字延迟** | `s.first − s.start`，max / min / 算术平均 | |
| **解码输出 · 平均** | `Σ_s s.out ÷ Σ_s (s.last − s.first)` | token 加权，与胶囊左侧同值 |
| **解码输出 · 合计** | `Σ_s (s.last − s.first)` | |
| **预填充输入 · 平均** | `Σ s.inp ÷ Σ (s.first − s.start)` | 估算，只算 `inp>0` 的步 |
| **预填充输入 · 合计** | `Σ (s.first − s.start)`，同上范围 | |
| **本轮解码速度** | 各步 `s.out ÷ (s.last − s.first)` 的 **p10 ~ p90** | 仅窗口 ≥ 100 ms 的步，标「估算」 |
| **本轮预填充速度** | 各步 `s.inp ÷ (s.first − s.start)` 的 **p10 ~ p90** | 标「估算」 |
| **总用量** | 输入 `Σ s.inp`；输出 `Σ s.out` | |

恒等式（实现里有断言）：

```
解码平均 × 解码合计 = 输出 token
模型耗时 + 工具耗时 = 总耗时
```

**显示格式**

- 时长：`42秒` / `1分55秒` / `3分00秒` / `1小时05分`，超过 1 小时不带秒。
- 速度：`< 100` 保留一位小数，`≥ 100` 取整。
- token：`745` / `≈8.4K` / `≈57.8K` / `≈1.1M`，只有真约分了才加 `≈`。

## 5. 需要知道的边界

### 5.1 「工具」包含什么

`工具 = 总耗时 − 模型耗时`，是残差而不是单独的计时器，因此它包含：
工具的实际执行、`turn/start → 首个 step` 的启动间隙、步骤之间的调度与审批等待、重试退避、
日志落盘与渲染间隙。

用一轮 241 秒的大轮次量过：`turn/start → 首个 step` 107 ms、`最后提交 → turn/end` 2 ms、
工具调用本身 169.8 s、模型 70.4 s——也就是说残差里 **99% 以上是工具执行**，
剩下的调度开销不足 1 秒（0.4%）。所以不再单列「其他」，直接并入工具。

### 5.2 速度区间为什么用 p10 ~ p90，而不是最小 ~ 最大

区间是**先按步算平均速度，再在这一轮的各步之间取分位数**。早期用的是 min ~ max，
在 644 步的实测里它被单个最好/最坏的一步主导：

| 指标 | min ~ max | 倍数 | p10 ~ p90 | 倍数 |
|---|---|---:|---|---:|
| 解码速度 | 26 ~ 3000 | **114×** | 184 ~ 413 | **2.2×** |
| 预填充速度 | 12 ~ 66531 | **5673×** | 84 ~ 887 | 10.5× |

两条原因：

1. **解码速度的极值来自短窗口**。`corr(解码窗口, 速度) = −0.285`：窗口越短算得越快，
   因为服务端可能把整段输出成批下发。实测最快一步是 69 token / 23 ms。区间因此同时
   排除窗口 < 100 ms 的步（占 5/644）。
2. **预填充速度的极值来自输入大小**。`corr(该步未缓存输入, 该步预填充速度) = 0.884`——
   由于 `速度 = 输入 ÷ 首字延迟` 而首字延迟几乎不随输入变化，小输入步被固定延迟主导
   （几十 tok/s），大输入步由算力主导（几万 tok/s）。所以预填充的区间主要反映**输入规模**，
   而不是速度波动；这一行请以「平均」为准。

### 5.3 其它

- **模型耗时含网络与首字延迟**：从请求发出算起。
- **工具耗时是残差**（`总 − 模型`），中断导致的审批等待、重试与调度都计入其中。
- **步骤没有时间线**时，该步不计入首字延迟、解码与预填充，但计入总用量与总耗时，其耗时落在「工具」里。
- **中断的步骤**按已产出的部分计入；未出首字时相关项为 `—`。
- 分叉会话继承父会话的事件，父会话的轮次也会出现在统计里。

## 6. 如何复算

```js
const recs = stream.filter(r => r.type !== 'chunk' && Array.isArray(r.dt) && r.dt.length > 0)
let first = null, last = null
for (const r of recs) {
  let acc = 0
  for (const d of r.dt) {
    acc += d
    const at = r.time0 + acc
    if (first === null || at < first) first = at
    if (last === null || at > last) last = at
  }
}
const ttft      = first - stepStart
const decodeWin = last - first
```

本仓库作者用一份**独立实现**（不 import 本包任何代码）对 26 轮真实会话做了 468 个字段的逐字段比对，结果零差异。
